# AGENT 执行工作流

## 总原则

先判定事件，再取数；事实靠联网，计算靠 MNS，判断留给投资者。每条结论必须能回答「这条信息从哪来、什么时候的」。

## Step 0 判定触发器

从用户话语或上下文中判定 A 现金流事件 / B 状态偏离 / C 计划外起意 / 复盘。信息不足时提问，不要用命令代替提问，也不要默认用户想买。

需要澄清时优先问这三个：

1. 这笔钱是计划内的新钱 / 月度定投，还是临时想追加？
2. 今天是例行检查，还是因为看到行情或消息才想起账户？
3. 有没有用钱需求或时间约束？

判定结果写入决策卡。涉及金额时必须由用户给出，不自行假定月投额（`cashflow.monthly` 当前为 0，`mns plan` 不带 `--monthly` 会报错）。

## Step 1 只读采集

运行 `scripts/collect_state.sh`，按需附加 `--monthly <金额>` 与 `--mirror`。脚本收集生效配置、现金、持仓、绩效、流水、冷静期、数据新鲜度；全部为只读命令。

明确禁止在采集阶段调用：`today`、`report`、`update-prices`、`sentiment`、`buy`、`sell`、`cash deposit`、`cash withdraw`、`cash set`、`add`、`remove`、`price <值>`、`backtest update-data`。这些会写快照、价格或台账，属于决策后动作。

若 `guard` / `plan` 报「本地没有恐贪快照」，说明本地快照缺失：向用户说明 `mns report` 会写入当日 FGI 快照与资产快照，征得同意后再跑一次；或改读 `reports/` 下最近一份报告，并标注其日期。

## Step 2 联网核验

按 `live-verification.md` 执行。每条核验结果记录「查到的值 + 来源 + 日期」，并与 `mns config` 输出的静态假设逐项比对。

只把联网结果用于：判断这笔交易能不能按计划执行、成本或到账是否变了、标的是否发生影响执行的事件。**不得**用于判断买卖方向。

## Step 3 用 MNS 计算

- 买入金额取 `mns plan --monthly <金额>` 的「本月买入」列与标的分配。
- 再平衡金额取决策日 `mns report` 的调仓计划与净操作指引。
- 不自行重算目标仓位、偏离或缺口；不把核验结果折算成「修正后的仓位」。
- `plan`（分母含本月新钱）与 `report`（分母为当前现金 + 持仓）金额不同属正常，分别解释，不调和成一个数。
- QDII 限购、结算天数只改变执行排期，不改变买什么、买多少的决策合法性。

## Step 4 输出决策卡

固定结构，不因结论是「不操作」而省略：

```
触发器：A / B / C / 复盘
本周是否操作：是 / 否
依据：
  - [MNS 计算] 决策分数、目标/当前权重、偏离、建议金额、年度已操作笔数
  - [联网事实 · YYYY-MM-DD · 来源] 限购、费率、交易日、标的事件
  - [用户陈述] 金额、用途、时间约束
  - [推断] 仅放明确标注为推断的内容
动作：买 / 卖 / 不动；标的、金额、排期（含限购拆分与 T+n）
不动作或例外原因：逐条对应 buy-sell-playbook.md 的判定链
待人工确认：需要用户拍板的事项
来源与时效：数据新鲜度、快照年龄、价格陈旧天数
```

禁止出现的字段：预期收益、目标价、胜率、「买点 / 卖点」「看好 / 看空」。

「不操作」也要写完整卡片，并说明下一个可能的触发时点（下一个决策日、下次发薪日、数据修复后）。

## Step 5 留痕与复盘

- 实际成交后，经用户确认再用 `mns buy <代码> <份额> <价格>` / `mns sell ...` 登记；登记是台账动作，不是下单。
- 用 `assets/decision-record.md` 保存本次决策理由，尤其是 C 类计划外起意的最终处理。
- 复盘对照以下指标，不对照收益率：

| 指标 | 取数 |
|---|---|
| 年度交易笔数是否在 10–20 预算内 | 决策版报告第 5 行 / `mns history` |
| 非计划交易次数 | 决策记录 vs 流水 |
| 严格执行与实际的偏离 | `mns backtest mirror` |
| 受阻与费用次数 | mirror 输出（限购、在途资金、费用） |
| 配置假设过期次数 | 联网核验记录 |

## 失败与升级

| 情况 | 处理 |
|---|---|
| CNN 接口失败、快照 ≤7 天 | 照常决策，卡片标注情绪数据滞后 |
| 快照 >7 天 / 价格陈旧 ≥1 天 / 数据超 30 天 SLA | 输出「不操作」，先修复数据，不用 `--decide` 绕过 |
| 限购或暂停申购 | 保留原决策金额，给出分日 / 分标的排期，说明不改变买入理由 |
| 联网核验与配置不一致 | 标注「MNS 计算基于旧假设」，建议用户确认后用 `mns config <键> <值>` 更新；不自动改配置 |
| 用户要求预测涨跌、给买卖点 | 明确说明该能力已被证伪，改给触发器判定与执行核验 |
| 用户要求自动下单或直接改台账 | 拒绝代执行，给出待用户确认的命令清单 |
| 用户坚持要做计划外大额买入 | 不否决，给 `guard` 的 1 日延迟 + 写理由，并把该决定留痕 |

配置改动会同时影响 `mns report` 与 `mns backtest`（同源信号），因此任何参数变更都必须由用户确认，且不得为了「让这次买入看起来更合理」而调整。
